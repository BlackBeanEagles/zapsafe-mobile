## 1. What was actually wired

### `mg_gunshot_retrain` — new detection family (gunshot)

Confirmed directly against the real file
(`interpreter.get_input_details()`/`get_output_details()`, TF 2.17) and the
real training script (`day261_mg_gunshot_retrain.py`), **not** assumed to
match m1_scream_v2:

- Input: `[1, 128, 128, 3]`, **int8**, scale=0.003921568859368563,
  zero_point=-128.
- Output: `[1, 1]`, int8, scale=0.00390625, zero_point=-128.
- Preprocessing (`audio_to_melspec` in the training script): sr=16000
  (not m1's 22050), 3.0s window (48,000 samples), 128 mels, hop=512,
  n_fft=2048, **fmax=8000** (not m1's implicit Nyquist), `power_to_db`
  + per-clip min-max to `[0,1]`, then **`np.resize(mel_norm, (128,128))`**
  (wrap/tile, not an image resize — the real mel is `[128, 94]` for a 3s
  clip at these settings, so every output row past the first ~94 columns
  repeats earlier data), stacked into 3 identical channels
  (`np.stack([img,img,img], axis=-1)`), then int8-quantized.

Files:
- `lib/data/services/gunshot_detector.dart` (`GunshotDetectorV2`) — full
  preprocessing + int8 quantize/dequantize using the real scale/zero_point
  read from the loaded interpreter (not hardcoded).
- `lib/data/services/gunshot_audio_pipeline.dart` (`GunshotAudioPipeline`)
  — native PCM stream -> 16kHz resample -> `GunshotDetectorV2`, structurally
  identical to `ScreamAudioPipeline`.
- `lib/data/services/mel_spectrogram.dart` — added an optional `fmax`
  parameter (defaults to `sampleRate/2`, so m1's existing behaviour is
  unchanged) to support the `fmax=8000` cap.
- `assets/models/mg_gunshot_retrain.tflite` — copied from the real Kaggle
  output, verified 2,874,160 bytes matches on disk.

**Parity tests** (`test/gunshot_detector_test.dart`, all passing — see §3):
mel spectrogram values checked elementwise against real librosa at
mg_gunshot's actual params (`test/fixtures/mel_golden_gunshot.json`,
generated by librosa 0.11.0 locally, not assumed); the `np.resize` wrap/tile
step checked against real `numpy.resize` output
(`test/fixtures/np_resize_wrap_golden.json`) plus a hand-verified small
case; int8 quantization checked against the real model's own scale/
zero_point (`test/fixtures/gunshot_quant_golden.json`).

### `m2_motion_b_retrain` — second, independent fall detector

Confirmed directly against the real file: input `[1, 128, 6]`, **float32**
(not int8 — see "real discrepancy found" below), no quantization params
(`quantization: (0.0, 0)`). Output `[1, 1]` float32.

Preprocessing (`day261_m2_motion_b_retrain.py`): `IMU_LEN=128`,
`IMU_DIM=6`, `G_RANGE=8.0`, `normalize(w) = clip(w, -8, 8) / 8` — a fixed
symmetric clip+scale, **not** m2_motion_v2's per-channel mean/std
standardisation.

**Design decision — kept as a second, independent detector, not merged
into `m2_motion_v2`.** `m2_motion_v2` is already wired and shipping
(Day 259). `m2_motion_b_retrain` replaces a previously-dead checkpoint
(`m2_motion_b`/`m2_motion_adversarial`, bit-exact 0.0 on real UCI-HAR
before this retrain — `DAY260D_M2_MOTION_B_CHECK.md`) with a different
architecture (`medium_cnn1d`), different window length (128 vs 100
samples), and different real training data (SisFall fall-impact positives)
than m2_motion_v2. Fusing the two or gating one on the other would risk
silently changing m2_motion_v2's already-verified real-world behaviour for
no documented benefit. The simplest, safest choice that ships correctly
today: both run independently, both can independently fire, both are
tagged with distinct event types (`motion` vs `motion_b`) so the data can
be analysed — and one deprecated, or the two properly fused into an
ensemble — once there is field evidence for which fires more reliably.

Files:
- `lib/data/services/motion_detector_b.dart` (`MotionDetectorB`,
  `MotionWindowBufferB`).
- `lib/data/services/motion_audio_pipeline_b.dart`
  (`MotionAudioPipelineB`) — structurally identical to `MotionAudioPipeline`.
- `assets/models/m2_motion_b_retrain.tflite` — copied from the real Kaggle
  output, verified 60,272 bytes matches on disk.

## 2. Real discrepancy this session found (doc vs. real file)

`DAY261B_KAGGLE_RUNS.md` calls `m2_motion_b_retrain.tflite` an "int8
tflite" by file-size convention (58.9KB matches `int8_kb: 58.9` in the
training report). **The exported file's input/output tensors are actually
float32 with no quantization parameters** — confirmed directly via
`interpreter.get_input_details()`/`get_output_details()` on the real file,
not assumed from the doc. This is a *dynamic-range-quantized* model
(int8 weights internally, for size — hence the small file — but float32
I/O), which is a real and different thing from `mg_gunshot_retrain.tflite`,
whose input/output genuinely are int8 tensors requiring explicit
quantize/dequantize at inference. `MotionDetectorB.tryLoad()` asserts
`float32` and fails loudly (returns null, logs in debug mode) if that
ever stops being true — the same defensive pattern `MotionDetectorV2` and
`ScreamDetectorV2` already use for their own shape assertions.

## 3. Backend schema change

`zapsafe_backend/ml/models.py` — `EventType` gained `GUNSHOT = "gunshot"`
and `MOTION_B = "motion_b"` (first additions since Day 55; both fit within
the existing `max_length=10` field, so no column type change is needed).

Migration: `ml/migrations/0008_alter_detectionevent_event_type.py`
(`makemigrations ml`). `sqlmigrate ml 0008` output (run for real inside the
`web` Docker container against the real Postgres `db` service):

```sql
BEGIN;
--
-- Alter field event_type on detectionevent
--
-- (no-op)
COMMIT;
```

A no-op ALTER — this is purely a Django-side `choices=` metadata change;
the column itself (`CharField(max_length=10)`) doesn't need to change to
hold `"gunshot"` (7 chars) or `"motion_b"` (8 chars). Applied for real:

```
$ docker compose exec web python manage.py migrate ml
Operations to perform:
  Apply all migrations: ml
Running migrations:
  Applying ml.0008_alter_detectionevent_event_type... OK
```

`ml/serializers.py`'s `DetectionEventSerializer.validate_event_type`
already validates dynamically against `EventType.values`, so no serializer
change was needed. `ml/views.py`'s event-type query filter (`event_type in
EventType.values`) is likewise dynamic — confirmed both, no hardcoded
event-type lists found anywhere in `ml/serializers.py` or `ml/views.py`.
