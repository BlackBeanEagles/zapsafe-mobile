# Day 260C — reconciling the two unresolved Day 259-vs-today discrepancies

Follow-up to `DAY260_QUANTIZATION_ROOTCAUSE.md` Finding 1 (`m_glass_breaking`
did not reproduce Day 259's "exactly constant, AUC 0.500" on ESC-50) and
`DAY260B_HIDDEN_INPUT_CHECK.md` Step 3 (`o_running_fleeing` did not reproduce
Day 259's "collapses to exactly 0 on fall-injected" using the model's own
`apply_panic_running()` augmentation). Both were left flagged, not resolved,
in those docs — this is now a repeating pattern (2 of ~5 models checked so
far disagreed with Day 259), which matters because if Day 259's harness had
a systematic bug, all 20 of its "0 passed" verdicts would be suspect.

Script that produced every number below:
`tools/day260_ml_triage/check_harness_reconciliation.py`. Re-run it to
reproduce — raw command output is pasted, not retyped, throughout this file.

## What could actually be reconstructed of Day 259's methodology

`triage.py` itself was never committed (`git log --all -p -- '*triage*'`
returns nothing — the only trace of it is `ebc50f6`'s commit message and
`PREPROCESSING_SPEC.md`'s Day 259 table, both of which describe *outcomes*,
not the harness code). What Day 259's own commit message and doc text
*do* state, read literally:

- Commit `ebc50f6`: "Built a real-data harness ... that, for each model,
  recovers its own training config from its own script, decodes real
  ESC-50/AudioSet/UCI-HAR data through it". **AudioSet is explicitly named**
  as one of three real data sources — not just ESC-50 and UCI-HAR.
- `PREPROCESSING_SPEC.md`'s Day 259 section header: "Ran every model whose
  training config could be recovered against real, labelled data
  (`DS07_AudioSet/train_wav`, `DS21_ESC-50`, `DS11_UCI-HAR`)." All three are
  named as real sources available to the harness, not tied to a specific
  model row.
- The per-family "Recovered per-family configs" block documents
  `m_glass_breaking`'s preprocessing as `minmax 1e-8` only — it does **not**
  say which of ESC-50 or AudioSet supplied the real positives for this
  specific model, unlike `mg_gunshot`'s row which is unambiguous (Day 259's
  own table already shows `mg_gunshot_f32` scored AUC 0.373 "worse than
  chance" — consistent with real AudioSet gunshot audio, which
  `DAY260_QUANTIZATION_ROOTCAUSE.md` Finding 2 also used and got AUC 0.538,
  same ballpark, same conclusion).
- For `o_running_fleeing`, Day 259's own verdict says "responds to real
  walking data (std 0.18) but collapses to exactly 0 the instant a real fall
  is injected". The word **"fall"** is used deliberately and specifically —
  not "panic", not "running", not "flee". `day94_o_running_fleeing.py` has
  no fall-related function anywhere in it (confirmed by grep — see below);
  its only injection function is `apply_panic_running()`, used for the
  RUNNING/panic-flee positive class. A "fall" is a different physical event
  from "panic running" by this script's own class definitions.

Neither of these fully proves what Day 259's harness did, but both point in
the same direction tested below: **harder, out-of-distribution, or simply
differently-labelled real data than what Day 260/260B used first.**

No `apply_fall` function exists anywhere in the repo. Whatever "fall" data
Day 259 used, it was not generated by any model's own training script.

## Test 1 — `m_glass_breaking`: real AudioSet glass/shatter/smash audio (day93's own label lists), not ESC-50

Hypothesis: the model is genuinely good on its own training distribution
(ESC-50, which is very likely *literally in the model's training set* — the
day93 script trains on `ESC_POS_CATS = {"glass_breaking"}`) and fails hard
on more realistic, noisier, out-of-distribution real audio, such as
AudioSet's much larger and messier glass/shatter/smash-labelled clips. Used
`day93_m_glass_breaking.py`'s own `GLASS_MIDS`/`GLASS_TERMS` (positive
match) and `NEG_MIDS`/`NEG_TERMS` (hard-negative match) verbatim — not
re-derived by guess — against real AudioSet clips present locally.

```
======================================================================
TEST 1: m_glass_breaking on real AudioSet glass/shatter/smash audio
(day93_m_glass_breaking.py's own GLASS_MIDS + GLASS_TERMS + NEG_MIDS/NEG_TERMS)
======================================================================
real AudioSet glass-labelled clips found locally: 106
real AudioSet hard-neg (day93 NEG_MIDS/NEG_TERMS) clips found locally: 5090
final set: n=80 pos=40 neg=40

--- fp32 -- real AudioSet glass audio ---
n=80  std=0.147888  min=1.87514e-07  max=0.964854  mean=0.0395047
pos median=0.000265249 (n=40)  neg median=0.000819363 (n=40)
AUC=0.3744

--- int8 staged -- real AudioSet glass audio ---
n=80  std=0.121686  min=0  max=0.851562  mean=0.0446289
pos median=0.00390625 (n=40)  neg median=0.00390625 (n=40)
AUC=0.4744
```

**Result: this is a close, though not byte-exact, reproduction of Day 259's
verdict.** It is not literally std < 1e-4 / AUC exactly 0.500 — a handful of
AudioSet clips per class pull scores up as high as 0.85–0.96, which keeps
the raw std above the "exactly constant" threshold. But the signal that
actually matters for a usability verdict is gone: AUC is at or below chance
(0.37 fp32, 0.47 int8), and **the int8 file's pos and neg medians are
bit-for-bit identical (0.00390625 both)** — i.e., for the median case in
each class, the model outputs literally the same number regardless of
label, the same "quantization noise, not signal" pattern Day 259's table
used to describe several other models (`m4_vocal_stress_en_adversarial`,
`m5_vocal_stress_apac_adversarial`). Compare directly against today's
earlier ESC-50 result (`DAY260_QUANTIZATION_ROOTCAUSE.md` Finding 1):
AUC 0.97 fp32 / 0.89 int8, clean pos/neg separation.

**Conclusion: `m_glass_breaking` performs well on audio close to its own
training distribution (ESC-50) and fails — at or below chance, with
indistinguishable pos/neg medians on int8 — on harder, more realistic
AudioSet audio.** This is consistent with hypothesis 1 from
`DAY260_QUANTIZATION_ROOTCAUSE.md` ("the model genuinely is constant [or
near-so] on that harder, more realistic distribution while looking fine on
ESC-50, which is also literally what the model was trained on"). Day 259's
"exactly constant" wording is a stronger claim than what reproduces here
(real std is 0.12–0.15, not 0.0), which could be explained by a smaller or
differently-sampled real subset, or a slightly different match list, that
this test does not exactly replicate — but the underlying safety-relevant
conclusion (do not ship, no usable real-world signal) matches Day 259's
call, not today's earlier ESC-50 result.

## Test 2 — `o_running_fleeing`: real SisFall fall-impact IMU data, not `apply_panic_running()`

Hypothesis: Day 259's "fall" meant an actual fall-impact IMU event — a real,
different physical signal from panic/fleeing running — not this model's own
RUNNING-class augmentation. `ml_datasets/motion/DS13_SisFall/Three Classes/`
has a real, preprocessed SisFall test split (`x_test_3`/`y_test_3`, 18,884
windows, 256 samples x 6 channels, 3-class one-hot: class 0 = ADL
[n=18,180], class 1 = Fall [n=157], class 2 = near-fall [n=547] — class 1
identified as "Fall" by being the rarest class, matching SisFall's known
fall-vs-ADL class imbalance). Each real 256-sample window was resampled
(linear interpolation, not synthesized) to the 128-sample window
`o_running_fleeing` expects — a real recorded waveform, only its sample
count changed to match the model's input shape.

```
======================================================================
TEST 2: o_running_fleeing on real SisFall fall-impact IMU data
======================================================================
SisFall test split total windows: 18884  class counts (ADL/Fall/NearFall): [18180   157   547]
real SisFall fall windows used: 60  real SisFall ADL windows used: 60

--- fp32 -- real SisFall ADL (calm) ---
n=60  std=0.21859  min=1.46222e-32  max=0.999829  mean=0.0645889

--- fp32 -- real SisFall FALL (impact) ---
n=60  std=5.135e-08  min=3.19966e-12  max=3.47035e-07  mean=1.79327e-08
fp32: ADL mean=0.0645889  FALL mean=1.79327e-08  delta=-0.0645889

--- int8 staged -- real SisFall ADL (calm) ---
n=60  std=0.218599  min=1.48319e-32  max=0.999831  mean=0.0645873

--- int8 staged -- real SisFall FALL (impact) ---
n=60  std=5.34208e-08  min=3.72504e-12  max=3.5965e-07  mean=1.88051e-08
int8 staged: ADL mean=0.0645873  FALL mean=1.88051e-08  delta=-0.0645873
```

**Result: this reproduces Day 259's numbers closely.** On real SisFall fall
windows, both fp32 and int8 collapse to ~1.8e-8 — the score is, to six
decimal places, exactly 0, with std ~5e-8 (floating-point noise, not real
variance) — matching Day 259's "collapses to exactly 0 the instant a real
fall is injected" almost exactly. This is the opposite of today's earlier
`apply_panic_running()` result (score moves *up*, mean 0.084, on real
UCI-HAR windows put through the model's own panic augmentation).

**Both results are real and both reproduce correctly — they are simply
different real stimuli.** `o_running_fleeing` is trained (per
`day94_o_running_fleeing.py`'s own class definitions) to detect RUNNING /
panic-flee IMU signatures versus walk/sit/stand, not falls. A real fall
(sudden freefall then impact, then stillness) is a different physical event
from panic running (sustained high-cadence bursts with directional
jitter), and this model was never trained to treat it as a positive. Its
near-zero output on real fall data is therefore not a "wrong-direction"
defect in the sense of a broken model — it is the model correctly
reporting "not panic running" on data that, semantically, was never in its
positive class.

Whether Day 259's own "wrong-direction, unusable" framing was itself a
fair characterization is a separate, harder question this doc does not
resolve: if the deployment intent for `o_running_fleeing` is "detect any
kind of person-in-danger IMU signature, falls included," then near-zero on
real falls is a real product gap (the model needs fall data in training, or
`o_running_fleeing` needs to be paired with a separate fall detector). If
the intent is narrowly "detect panic running specifically" (which is what
the model was actually trained and named for), near-zero on fall data is
correct, in-spec behavior, and the original "wrong-direction" framing
overstates the problem. **This doc takes no position on which intent is
correct — that is a product decision, not a measurement one — but the
measurement itself is now reconciled: Day 259's raw numbers are reproduced
with real fall data, and today's raw numbers are reproduced with real
panic-running data. Neither harness was wrong; they tested different real
stimuli.**

## Blast-radius assessment

**Day 259's harness does not appear to have had a systematic bug.** Both
discrepancies resolve to the same root cause: Day 259 used harder,
differently-sourced, or differently-labelled real data than Day 260/260B's
first-pass tests did, and — for both models — the harder/differently-typed
real data reproduces Day 259's numbers far more closely than the easier
data did. This is the opposite of what would be expected if Day 259's
measurement code itself were broken (a broken harness would be expected to
produce *implausible* numbers under a correct re-test, not numbers that
reappear the moment a harder or more literally-matched real dataset is
substituted in).

This means: **Day 259's other 18 "0 passed" verdicts should be treated as
likely trustworthy, not suspect**, with two already-known, narrower
exceptions that are unrelated to this finding and were already corrected in
prior docs:

- `k_confinement`/`k_best` and `s_crowd_panic_a`/`s_best` — genuinely
  measured with an undocumented second input left unset
  (`DAY260_QUANTIZATION_ROOTCAUSE.md` Finding 3,
  `DAY260B_HIDDEN_INPUT_CHECK.md` Step 4). This is a real, distinct bug
  class (missing tensor, not a real-data-source difference), already fixed
  and already reflected in `PREPROCESSING_SPEC.md`'s tensor-shape table.
  `s_crowd_panic`'s wrong-direction verdict was independently **confirmed**
  even after the fix; `k_confinement`'s "exactly constant" verdict does not
  hold as originally worded but the corrected model is still architecturally
  degenerate (light-gated).

No other model's Day 259 verdict is contradicted by today's or this doc's
testing.

## What should be re-tested next

- **`m2_motion_b`, `m2_motion_adversarial`** — still the one genuinely open
  item across all three Day 260-series docs. Confirmed single-input
  (`DAY260B_HIDDEN_INPUT_CHECK.md`), confirmed **not** int8-quantised
  (contradicting the original "quantisation collapse" narrative for these
  two specifically), and never re-tested against real data at all. Given
  today's finding that harder/differently-sourced real data is what
  reproduces Day 259-style failures, the right next step is the same
  pattern applied here: find these two models' own training script,
  recover their real positive-class augmentation function, and test against
  real UCI-HAR/WISDM/PAMAP2 data run through it — not a synthetic
  placeholder signal.
- No other re-test is indicated by this doc's findings. `mg_gunshot`,
  `i_vehicle_crash`, `n_breathing_distress`, and the `96x96` day101 family
  were not touched today, but nothing found today gives a reason to doubt
  their Day 259 numbers specifically.
