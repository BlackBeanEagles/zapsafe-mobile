## 2. Preprocessing, from `day95_s_crowd_panic.py` (the Day 264 fixed version)

**Audio side** (`audio_to_mel`): `SR=16000`, `DURATION=2.0s` (32,000
samples), `n_fft=2048`, `hop_length=512`, `n_mels=64`, `fmax=8000`,
`librosa.power_to_db(mel, ref=np.max)` — **no per-clip min-max rescale**,
unlike m1_scream_v2/mg_gunshot. Frames = 63 for a real 2.0s/16kHz clip
(`1 + 32000 // 512`), zero-padded by 1 column to the fixed 64x64 shape.
Final scaling is a **global** `(mel - mel_mean) / mel_std` using constants
baked into `s_crowd_panic_norm.json` (`mel_mean=-16.599195...,
mel_std=17.935195...`), read from the bundled asset at load time, not
hardcoded.

**IMU side**: raw `[128, 6]` window (acc xyz + gyro xyz), same convention
and window length as `MotionDetectorB`/`m2_motion_b_retrain` — reused
`MotionWindowBufferB` for windowing. Normalised with a **global
per-channel** `(imu - imu_mean[c]) / imu_std[c]`, a third distinct
normalisation convention from both `m2_motion_v2`'s live per-channel
standardisation and `MotionDetectorB`'s fixed `clip(-8,8)/8`.

`MelSpectrogram.compute()` (`lib/data/services/mel_spectrogram.dart`)
previously always did `power_to_db` *and* per-clip min-max together —
that's what m1/mg_gunshot need, but not what s_crowd_panic's training
script does. Added an optional `normalize` parameter (default `true`,
preserving existing callers exactly) so `compute(y, normalize: false)`
returns raw `power_to_db(ref=max)` with no min-max rescale — a new
`_powerToDb` helper alongside the existing `_powerToDbNormalised`.

## 3. Real discrepancy this session found

Reusing `MelSpectrogram.compute()`'s default behaviour for s_crowd_panic
(as a naive "just call the same helper" implementation would) would have
silently double-normalised the mel features: per-clip min-max to `[0,1]`
followed by a global `(x - mel_mean)/mel_std` that was fit on *un*-min-maxed
dB values in training. This is exactly the kind of trap
`DAY262_GUNSHOT_MOTIONB_WIRING.md`'s `np.resize` finding warned about — a
tensor of the right shape, scored on features the model never saw. Caught
by writing the real librosa parity fixture (`test/fixtures/
s_crowd_panic_mel_golden.json`, generated by librosa 0.11.0 locally) before
trusting the reused-helper reading and discovering it lands in dB range
(mean ≈ -71), not `[0,1]`.

## 4. Two-input fusion architecture — new code, not a copy of an existing detector

`lib/data/services/crowd_panic_detector.dart` (`CrowdPanicDetector`):
loads the model, verifies both input tensors by name (`imu`/`mel`
substring match on `interpreter.getInputTensors()[i].name`, not assumed
index order), verifies shape/dtype, loads `s_crowd_panic_norm.json` for
the real mel/imu mean/std constants, and runs a single fused inference via
`tfl.Interpreter.runForMultipleInputs([...], {0: [...]})` — the two-input
entrypoint `tflite_flutter` exposes (confirmed by reading
`tflite_flutter-0.10.4/lib/src/interpreter.dart` directly: `run()` is a
one-input special case of `runForMultipleInputs`).

## 5. Concurrent-capture design decision

`lib/data/services/crowd_panic_pipeline.dart` (`CrowdPanicFusionPipeline`)
subscribes to both the existing native audio-PCM stream and the
accelerometer/gyroscope streams (reusing `MotionWindowBufferB` for IMU
windowing, same as `MotionAudioPipelineB`). The two streams are
asynchronous and independent — audio ships a window roughly every 1s,
accelerometer samples arrive every ~10-20ms — so there is no built-in
instant where both sides are simultaneously fresh.

**Decision: cache the most recent window from each side; fire a fused
inference whenever either side produces a fresh window, provided the
other side's cached window is within `maxStalenessMs` (default 2500ms) of
now.** If the other side has never fired, or its last window is older than
`maxStalenessMs`, **no inference runs** — `windowsSkippedStale` counts
this rather than the pipeline silently falling back to stale or fabricated
data on one side. This trades perfect synchrony (not achievable without
blocking one sensor stream on the other, which no other pipeline in this
app does) for "never infer on data either side would call stale." Full
reasoning is in the class doc comment.

## 6. Backend schema change

`zapsafe_backend/ml/models.py` — `EventType` gained
`CROWD_PANIC = "crowd_panic"`. **Unlike Day 262's `gunshot`/`motion_b`,
this is not a same-width addition**: `"crowd_panic"` is 11 characters,
which does not fit the existing `event_type` column's `max_length=10`.
Widened `event_type` to `max_length=20` to leave room for future event
types of similar length.

Migration: `ml/migrations/0009_alter_detectionevent_event_type.py`.
`sqlmigrate ml 0009` output (run for real inside the `web` Docker
container against the real Postgres `db` service, which was already
running from a prior session):

```sql
BEGIN;
--
-- Alter field event_type on detectionevent
--
ALTER TABLE "ml_detectionevent" ALTER COLUMN "event_type" TYPE varchar(20);
COMMIT;
```

A real `ALTER COLUMN TYPE`, not a no-op — widening a `varchar` in Postgres
does not require a table rewrite (no data migration, fast metadata-only
change), so this is still safe to apply live. Applied for real:

```
$ docker compose exec web python manage.py migrate ml
Operations to perform:
  Apply all migrations: ml
Running migrations:
  Applying ml.0009_alter_detectionevent_event_type... OK
```

`ml/serializers.py`'s `DetectionEventSerializer.validate_event_type`
validates dynamically against `EventType.values`, and `ml/views.py`'s
event-type filter (`event_type in EventType.values`) is likewise dynamic —
confirmed both, no hardcoded event-type lists or length assumptions found.

## 9. What was not done / explicitly out of scope

- No on-device or emulator run — code-level verification only, matching
  how every prior model this week was verified.
- No field-tuned confidence threshold for `CrowdPanicDetector` — kept at
  the model's own raw sigmoid midpoint (0.5) since there is no published
  operating point yet beyond the training-split AUC and the real
  direction-check AUC (0.68, a real but not strong discriminator per
  `DAY264_S_CROWD_PANIC_MOBIACT.md`'s own verdict).
- `maxStalenessMs=2500` in `CrowdPanicFusionPipeline` is a reasoned default
  (audio window duration is 2.0s, audio stream hops ~1s), not something
  tuned against real field latency between the two sensor streams — flagged
  for revisiting once there is telemetry on `windowsSkippedStale`.
